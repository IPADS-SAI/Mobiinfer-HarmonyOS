# 跨机器补丁安全

- 从 Windows 向 Linux 传递补丁前，规范化为 LF 且移除 UTF-8 BOM，并先执行 `git apply --check`。
- 目标工作树已有未提交改动时，先比较待改文件的 Git blob 哈希；对重叠文件生成最小补丁或明确合并，不能直接覆盖整个工作树。
- 应用后同时执行 `git diff --check` 和关键源码断言，避免“补丁应用成功”掩盖未命中目标逻辑。
- 同步原生源码后，除工作区文件与 manifest 的哈希外，还须检查交付所用 Git index/commit 或归档是否包含所有新增头文件。服务器上能编译不代表另一台机器拉取后文件齐全；只提交已跟踪文件可能遗漏新增依赖。

# 厂商工具链与离线产物校验

- 替换 App 已下载模型中的文件前，检查下载 manifest、完成标记及大小/哈希校验。文件传输正确仍可能使模型状态失效；原地部署须同步对应下载记录，独立发布须提供与远端文件清单一致的完整运行包，再验证正常下载流程。
- 量化排查先建立同输入的两个独立参考：相同伪量化权重的浮点激活前向，以及校准 checkpoint 的权重/激活量化前向。先证实权重与前向一致，再区分量化固有误差和设备执行偏差；执行成功不代表数值正确。
- 加密压缩文件不能根据体积推断量化轴或是否包含激活。通过厂商 serializer 复现并校验参数，与实际导出图的算子输入及权重方向对照；未知配置字段只做独立实验，不直接修改交付模型。
- 量化配置须区分未指定与显式 false，报告优先读取校准状态；重载旧 checkpoint 可能恢复旧量化方式。配置修正后若序列化参数逐字节相同，应明确设备数值路径未因此改变，不能将配置合规当作精度故障已修复。
- 迁移厂商量化示例前，核对策略、位宽及平台算子 dtype 组合；工具接受配置不等于设备支持该融合路径。冻结已有量化状态，只校准新增状态，并先检查完整模型的量化参考偏移；小模型通过不能替代这一步。用户调整验收标准时记录新旧标准及复核结果，区分编译成功、数值一致和完整模型可用。
- SDK 初始化遇到沙箱权限错误时，先按权限流程复核完整环境，再判断算子支持情况；权限受限时的 unsupported 日志不能直接作为平台不支持的证据。单个融合算子的 dtype 表也不能穷尽编译器插入转换后的整图组合。
- 设备对照测试复用正式推理的 tensor descriptor、输入映射和数据类型转换，并记录 cosine 与 relative L2。仅 cosine 接近 1 会漏掉幅度缩放错误；所有实验应从同一份保存输入开始，避免误差串接。
- 厂商 serializer 或外部权重保存可能原地删除模型参数或改写 initializer。多候选实验应在副本上序列化，保留可重载的模型，并分别校验浮点数学、量化参考与设备输出；不能把浮点等价直接当作量化逐值等价。
- SDK 切换 LUT 等权重编码时，同名 fake_quant_weight 可能保存整数索引。必须重导配套 ONNX，先按 LUT 和 scale 还原后核对权重，不能沿用旧图或将索引当作浮点权重评估。
- 不要仅凭缺少惯例文件判断 SDK 或平台插件“不完整”。先以官方发行归档为信任根，校验归档哈希、版本元数据，并逐文件比对展开目录；禁止伪造缺失文件来绕过工具检查。
- SDK 自动部署须用真实发行归档验证解压和重复执行，保留插件内的相对符号链接与执行权限；用真实目标架构库检查同步结果，并用独立流程测试确认构建失败不会继续覆盖应用依赖。
- 编译器最终打印 `success` 只代表流程结束，不等于产物可用。应同时验证目标平台、固定输入、数据类型、压缩参数、设备分区、关键算子数量与逐算子 tiling/内核生成结果，并拒绝 CPU fallback 和致命诊断。
- 产物标注为 FP16 不代表权重来源仍是原始浮点模型。导出前应排除 fake-quant checkpoint/量化 hook，导出报告应记录权重来源与是否校准，并抽查 ONNX initializer 类型；否则可能把伪量化后的权重重新封装成 FP16，编译成功但精度已经改变。
- 厂商工具可能把可恢复的探测失败记录为 error 级日志。允许此类诊断前，必须证明它来自已校验的官方包，并要求每次失败都有对应的明确成功结果；未知错误不得加入宽泛白名单。
- 对“完整/一键”模型构建入口，必须明确列出源模型、量化权重、校准数据和厂商工具链等输入边界，并逐阶段验证产物；不能把仅生成最终设备产物的脚本描述成端到端构建流程。运行包可能不含审计用的导出 JSON 或冻结校准 checkpoint，复用前应检查完整性；精度报告须绑定对应权重、参考图及独立输入的哈希，失败后不可沿用旧通过状态。
- 厂商编译器的路径校验可能严于文件系统；端到端验证要覆盖默认工作目录。必要时在可配置、字符受限的临时目录中暂存字节一致的输入，再校验并搬回产物，避免要求用户改动源模型目录。
- 自动下载模型时区分默认缓存与用户显式提供的目录；缺失的自定义输入不能被默认模型悄悄替换。记录仓库、版本与下载完成状态，检查所有分片，覆盖中断后已有权重文件但下载未完成的情况；先检查必需的本地 SDK，再触发大文件下载。

- 参考其他推理框架的图权重分离时，逐项核对编译开关、外部文件布局、设备初始化 API 和对象生命周期；先用真实模型编译探针证实可行，再迁移加载逻辑。磁盘去重、executor 常驻、设备权重共享是不同能力，分别取证。
- 可选动态 API 不能仅以 `RTLD_DEFAULT` 查找失败判断不支持。复核参考实现使用的库句柄和加载作用域，保留 loader 错误与实际 provider；回归测试须使用真实 `RTLD_LOCAL` 共享库，分别覆盖仅局部可见、缺符号和缺库，避免全局导出的测试替身掩盖部署差异。
- 模型回答无关时，用相同权重分别测试权重单独量化与完整激活量化，并检查截断范围；范围修正须保留独立样例和失败门槛，不能以更大范围、更高余弦或少数回答恢复代替完整精度验收。

# 任务反思与经验沉淀

> **触发条件**：任何非平凡任务完成后（尤其是经历了 debug 的任务），主动执行此 skill。也可由用户显式触发。
>
> **服务对象**：所有 skill。本 skill 的产出是对其他 skill 文件的更新，不产生代码。

## 核心原则

### 🚨 对结果要有定力，不要自我欺骗

最大的风险是"觉得差不多了"的幻觉——结果不达标时，找外部原因搪塞然后降低要求宣布完成。

**常见的自我欺骗模式：**
- **功能任务**：输出不正确时归因于"量化精度不够"、"模型太小"、"这是预期的退化"，而不是继续排查实现 bug
- **性能任务**：优化没有效果时归因于"编译器已经优化得很好了"、"已经接近理论极限"，而不是继续尝试其他方案

**正确做法：**
- 测试目标在开始前就定好，不能中途降低标准
- 通过标准必须具体、可验证（"差不多能用"不算通过）
- 功能任务：人工验证不通过就是没通过，继续排查实现细节
- 性能任务：没有达到预期提升就继续优化，用数据证明已到极限而不是猜测

### TDD 思维：先定测试再写代码

每个子任务开始前明确三件事：
1. **通过标准是什么？** — 具体的预期输出
2. **怎么测？** — 可执行的测试命令
3. **什么不算通过？** — 明确列出容易自我欺骗的边界情况

## 执行流程

### 1. 识别教训

- 走了哪些弯路？错误假设是什么？
- 根因是什么？为什么没有第一时间找到？
- 方法论问题？跳步了？过早下结论了？把 bug 归因为外部原因了？

### 2. 判断归属

| 教训类型 | 更新位置 |
|---------|---------|
| 某个 skill 流程中的陷阱 | 该 skill 的 `common-pitfalls` 或步骤文件 |
| 通用工作方法论 | 该 skill 的 SKILL.md 顶层注意事项 |
| 跨 skill 通用经验 | memory 系统 |

### 3. 写入原则

- **只写方法论，不写单次任务的具体细节。** 可以附最小测试示例说明如何验证。
- **放在最显眼的位置。** 关键教训放 SKILL.md 顶部，不要埋在子文档末尾。
- **增加的同时审视现有内容。** 显而易见的、能从代码直接推出的指导删掉或精简。单个步骤文件不超过 500 行。
